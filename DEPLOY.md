# Deploying Traceforge

Two ways to put Traceforge on the internet:

- **[Render (free plan)](#render-free-plan)**: quickest. A public HTTPS address in minutes, no server to manage.
  Good for demos; the free plan has real limits (below).
- **[Your own server](#your-own-server-vps)**: one Linux VPS behind Caddy. More work, no platform limits.

---

## Render (free plan)

Repository: **<https://github.com/hemanth210205/Trace-forge>** (branch `main`). It contains everything Render needs:
[`render.yaml`](render.yaml) (a Blueprint that creates the web service and a free PostgreSQL 16 database in the
Singapore region), a [`Dockerfile`](Dockerfile) that builds the console and the API into one image, and
[`deploy/render-start.sh`](deploy/render-start.sh).

### What the free plan means

> **Your data on the free plan is temporary.** The free database **expires 30 days after it is created**. After a
> further **14-day grace period**, Render **deletes it with all its data**. Free databases have **no backups** of any
> kind. Export what you want to keep before day 30 (R5), or upgrade the database to a paid plan.

| Free-plan fact (Render's documentation) | Consequence |
| --- | --- |
| **Database expires 30 days after creation**, then is **deleted after a 14-day grace period** | Plan for it: export before day 30 or upgrade. A new free database starts empty |
| **No backups** of free databases; 1 GB storage; only one free database per workspace | Your exports are the only copy of your data |
| **Cold starts**: the service spins down after 15 minutes without traffic; the next request waits about a minute while it starts | Open the site a minute before you show it. Work interrupted by a spin-down is marked failed after the restart |
| No shell and no pre-deploy command | Migrations run when the server starts (`TRACEFORGE_MIGRATE_MAIN_ON_START`); accounts are created **from your computer** (R2) |
| One instance; 750 free instance hours per workspace per month; Render may restart a free service at any time | Fits: Traceforge must run as a single instance anyway |
| Ephemeral filesystem (lost on every restart or spin-down) | Fits: Traceforge keeps everything in the database |

### R1. Create the service

1. Sign in at [dashboard.render.com](https://dashboard.render.com) (with GitHub) and allow Render to access the
   repository **hemanth210205/Trace-forge**.
2. **New → Blueprint**, pick the repository and branch `main`. Render reads `render.yaml` and shows a web service
   `traceforge` and a database `traceforge-db`.
3. Render asks for a value for `TRACEFORGE_MIGRATE_MAIN_ON_START`: enter `traceforge`. Then **Apply**.
   (Google/GitHub sign-in is added later, in R4, because the OAuth apps need the live address.)
4. Wait for the deploy. The first build takes a few minutes. When the log shows
   `Traceforge on database '<name>' at revision 0007`, the database was created and migrated.

   Render may give the database a suffix (for example `traceforge_lx31`). Then the first start stops instead, and
   nothing is written to the database:
   `Refusing to start: TRACEFORGE_MIGRATE_MAIN_ON_START must be the main database's exact name ('traceforge_lx31')`.
   Check the name under **traceforge-db → Info → Database**, set `TRACEFORGE_MIGRATE_MAIN_ON_START` to exactly that
   name in **traceforge → Environment**, and **Save changes**. The redeploy migrates the database.
5. Your address is shown at the top of the service page, e.g. `https://traceforge.onrender.com` (Render adds a suffix
   if the name is taken). Open `https://<your-address>/api/v1/health`: `{"status":"ok","database":"ok",...}`.

What `render.yaml` sets, and why:

| Setting | Value | Why |
| --- | --- | --- |
| `DATABASE_URL` | from the database | Render's private connection string (the `postgresql://` form is accepted) |
| `TRACEFORGE_SECRET_KEY`, `TRACEFORGE_API_KEY_PEPPER` | generated by Render | Random 256-bit values, created once |
| `TRACEFORGE_PUBLIC_BIND` | `true` | Lets the server listen on `0.0.0.0` behind Render's proxy. Refused unless the next two are set |
| `TRACEFORGE_COOKIE_SECURE` | `true` | Sessions only over HTTPS |
| `TRACEFORGE_TRUSTED_PROXIES` | private address ranges | Render's internal hop reaches the service from a private address. Forwarded headers are believed only from those ranges, so a client cannot spoof its address. Which address the rate limiter then sees on Render must be checked live: see [Client addresses on Render](#client-addresses-on-render-check-after-deploying) |
| `TRACEFORGE_MIGRATE_MAIN_ON_START` | entered by you: the database's exact name | Upgrades the database at start. Must equal the database name (which may have a suffix, see step 4); anything else stops the server. Kept in the dashboard (`sync: false`), so a Blueprint sync never resets it |
| `TRACEFORGE_REGISTRATION` | `invite` | Nobody can sign up without an invitation |
| Public URL, allowed host, trusted origin | your `onrender.com` address | Taken from `RENDER_EXTERNAL_URL` / `RENDER_EXTERNAL_HOSTNAME` by `deploy/render-start.sh` |

### R2. Create your account (from your computer)

There is no shell on the free plan, so run the account tool locally against the Render database:

1. In Render: **traceforge-db → Info → Connections → External Database URL** → copy. It contains the database
   password: never put it in a file, a chat, or a command line.
2. On your computer, with the same code as the deployment (`git pull` in your clone of
   <https://github.com/hemanth210205/Trace-forge>), open PowerShell in `backend\` and run:

   ```powershell
   # Paste the URL at the prompt. It is not shown, and not saved in PowerShell's command history
   # (history keeps the commands you type, not what you enter at a Read-Host prompt).
   $secure = Read-Host "External Database URL" -AsSecureString
   $env:DATABASE_URL = [System.Net.NetworkCredential]::new("", $secure).Password
   try {
       ..\.venv\Scripts\python -m app.accounts --database main user create you@example.com --name "Your Name"
   } finally {
       # Clear it from this PowerShell session even if the command fails.
       Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
       Remove-Variable secure -ErrorAction SilentlyContinue
   }
   ```

   The tool asks for the new account's password twice (also hidden) and prints `Created account you@example.com.`
   The database URL exists only in that PowerShell window's memory while the command runs.
3. Sign in at your address. To let someone else in, run the same block with
   `invite create their@email.com` instead of `user create ...`, and send them the printed link.

### R3. Check it

```powershell
$u = "https://<your-address>"
curl.exe -s "$u/api/v1/health"                      # {"status":"ok","database":"ok",...}
curl.exe -s "$u/api/v1/auth/registration"          # {"mode":"invite"}
```

Then run the two client-address checks below. They decide whether the login rate limit works per visitor on Render.

### Client addresses on Render (check after deploying)

Render does not document which client-address headers its proxies set. A third-party test service run on Render
([johnbeynon/header-test](https://github.com/johnbeynon/header-test), not official documentation) observed:

- `X-Forwarded-For` keeps whatever the client sent and appends the rest:
  `<client-supplied>, <real client>, 172.71.x.x, 10.x.x.x`. `172.71.x.x` is a Cloudflare address (Cloudflare's
  published `172.64.0.0/13`); `10.x.x.x` is Render's internal hop.
- A client-supplied `CF-Connecting-IP` is rejected by Cloudflare (`403`, error 1000); `True-Client-IP` is overwritten.

What that means for Traceforge's configuration (`TRACEFORGE_TRUSTED_PROXIES` = private ranges only):

- **Spoofing is not possible.** Reading `X-Forwarded-For` from the right, Traceforge skips only the private `10.x`
  hop and stops at the first address it does not trust, the Cloudflare one, so a client-supplied entry further left
  is never used. Cloudflare's ranges are deliberately *not* trusted: Cloudflare Workers make requests from Cloudflare
  addresses and can set `X-Forwarded-For` freely, so trusting those ranges would let anyone with a Worker choose
  their own address.
- **The rate limiter may count Cloudflare's edge address instead of the visitor.** If Cloudflare reaches Render from
  varying edge addresses, failed logins would be spread over several counters (weaker brute-force throttling); if many
  visitors share one edge address, one person's failures could lock others out.

Check which applies to your deployment (both take a few seconds; use an email that has no account):

```powershell
$u = "https://<your-address>"
$body = '{\"email\":\"rate-limit-check@example.com\",\"password\":\"wrong\"}'

# Check 1 - spoofing: a different fake X-Forwarded-For on every attempt.
1..7 | % { curl.exe -s -o NUL -w "%{http_code} " -X POST "$u/api/v1/auth/login" -H "Content-Type: application/json" -H "Origin: $u" -H "X-Forwarded-For: 203.0.113.$_" -d $body }; ""

# Check 2 - stable counting: wait 15 minutes (the limit window) or change the email, then no headers at all.
$body = '{\"email\":\"rate-limit-check-2@example.com\",\"password\":\"wrong\"}'
1..7 | % { curl.exe -s -o NUL -w "%{http_code} " -X POST "$u/api/v1/auth/login" -H "Content-Type: application/json" -H "Origin: $u" -d $body }; ""
```

| Result | Meaning |
| --- | --- |
| Both print `401 401 401 401 401 429 429` | The limit counts you as one client and cannot be reset with headers. Nothing to change |
| Check 1 never reaches `429` | Spoofing works: stop and report it (this should not happen with the shipped settings) |
| Check 1 reaches `429` but check 2 does not | Not spoofable, but the counter follows changing Cloudflare addresses. Keep registration `invite` or `disabled` and treat the rate limit as weaker on Render until Traceforge reads `CF-Connecting-IP` for requests that verifiably came through Cloudflare (a code change, not yet made) |

Caveat: a single run shows what your connection sees, not every visitor's. Repeat check 2 from a second network
(for example a phone hotspot) to be more confident.

### R4. Google and GitHub sign-in (live address only)

1. **GitHub**: Settings → Developer settings → OAuth Apps → **New OAuth App**. Homepage `https://<your-address>`,
   callback `https://<your-address>/api/v1/auth/oauth/github/callback`. Generate a client secret.
2. **Google**: Cloud console → APIs & Services → OAuth consent screen (External; add your app name and email), then
   Credentials → **OAuth client ID** (Web application), authorised redirect URI
   `https://<your-address>/api/v1/auth/oauth/google/callback`. **Publish** the consent screen so anyone can sign in.
3. In Render: **traceforge → Environment → Add environment variable**, add `TRACEFORGE_GITHUB_CLIENT_ID`,
   `TRACEFORGE_GITHUB_CLIENT_SECRET`, `TRACEFORGE_GOOGLE_CLIENT_ID`, `TRACEFORGE_GOOGLE_CLIENT_SECRET` with the
   values from steps 1–2 → **Save changes** (Render redeploys). Add only the pair(s) you registered.
4. On the sign-in page, **Continue with GitHub / Google** now works. With `invite` registration, a *new* account
   still needs an invitation for the provider-verified email; your own account signs in directly if its email
   matches the one on GitHub or Google.

### R5. Keeping data and upgrading

- **Every push to `main` redeploys** (and migrates the database if the new version has a migration).
- **Before day 30**, export what you want to keep, or upgrade the database to a paid plan in Render. To export from
  your computer (needs PostgreSQL client tools, version 16 or newer: `pg_dump --version`), in PowerShell:

  ```powershell
  # 1. Read the URL at a hidden prompt, check it, and hand it to pg_dump through PostgreSQL's own environment
  #    variables, so no part of it appears on pg_dump's command line. Error messages never include the URL.
  #    "finally" removes every variable again, also when the URL is rejected or pg_dump fails.
  #    pg_dump writes to traceforge.dump.partial. Only a complete, readable export replaces traceforge.dump, so a
  #    failed run never damages your previous export.
  $final    = Join-Path (Get-Location).ProviderPath "traceforge.dump"
  $partial  = "$final.partial"
  $replaced = "$final.replaced"
  $exported = $false
  $swapping = $false
  $secure = Read-Host "External Database URL" -AsSecureString
  try {
      $url = [System.Net.NetworkCredential]::new("", $secure).Password
      $uri = $null
      if (-not [System.Uri]::TryCreate($url.Trim(), [System.UriKind]::Absolute, [ref]$uri)) {
          throw "That is not a URL. Copy the External Database URL from Render again."
      }
      if ($uri.Scheme -notin "postgres", "postgresql") {
          throw "Expected a postgres:// or postgresql:// URL, got $($uri.Scheme)://."
      }
      if (-not $uri.Host) { throw "The URL contains no host name." }
      # UserInfo is still percent-encoded, so the first literal ":" separates user and password;
      # an encoded colon (%3A) inside either is decoded only afterwards.
      $info = $uri.UserInfo
      $sep  = $info.IndexOf(":")
      if ($sep -lt 0) { throw "The URL contains no password (expected postgresql://USER:PASSWORD@HOST/DATABASE)." }
      $user = [System.Uri]::UnescapeDataString($info.Substring(0, $sep))
      $pass = [System.Uri]::UnescapeDataString($info.Substring($sep + 1))
      $db   = [System.Uri]::UnescapeDataString($uri.AbsolutePath.TrimStart("/"))
      if (-not $user)     { throw "The URL contains no user name." }
      if (-not $pass)     { throw "The URL contains no password." }
      if (-not $db -or $db.Contains("/")) { throw "The URL contains no database name (expected .../DATABASE)." }

      $env:PGHOST     = $uri.Host
      $env:PGPORT     = if ($uri.Port -gt 0) { "$($uri.Port)" } else { "5432" }
      $env:PGDATABASE = $db
      $env:PGUSER     = $user
      $env:PGPASSWORD = $pass
      $env:PGSSLMODE  = "require"    # encrypted connection to Render; never falls back to plain text
      Remove-Item -LiteralPath $partial -ErrorAction SilentlyContinue    # left over from an interrupted run
      pg_dump --format=custom --no-owner --file $partial
      if ($LASTEXITCODE -ne 0) { throw "pg_dump failed with exit code $LASTEXITCODE. traceforge.dump was not changed." }
      if (-not (Test-Path -LiteralPath $partial) -or (Get-Item -LiteralPath $partial).Length -eq 0) {
          throw "pg_dump wrote no data. traceforge.dump was not changed."
      }
      pg_restore --list $partial > $null
      if ($LASTEXITCODE -ne 0) { throw "The new export is not a readable archive. traceforge.dump was not changed." }

      # Publish. Replace() swaps the files in one step and keeps the old export as .replaced until it succeeded.
      $swapping = $true
      try {
          if (Test-Path -LiteralPath $final) {
              Remove-Item -LiteralPath $replaced -ErrorAction SilentlyContinue
              [System.IO.File]::Replace($partial, $final, $replaced)
          } else {
              [System.IO.File]::Move($partial, $final)
          }
      } catch {
          throw "Could not replace traceforge.dump (is it open in another program?). The previous export was kept. $($_.Exception.Message)"
      }
      $exported = $true
      Remove-Item -LiteralPath $replaced -ErrorAction SilentlyContinue
  } finally {
      Remove-Item Env:PGHOST, Env:PGPORT, Env:PGDATABASE, Env:PGUSER, Env:PGPASSWORD, Env:PGSSLMODE -ErrorAction SilentlyContinue
      # Interrupted (e.g. Ctrl+C) just after the swap: a failed Replace() or Move() always leaves .partial in
      # place, so a missing .partial next to traceforge.dump means the new export is in place. Finish as a success.
      if (-not $exported -and $swapping -and -not (Test-Path -LiteralPath $partial) -and (Test-Path -LiteralPath $final)) {
          $exported = $true
          Remove-Item -LiteralPath $replaced -ErrorAction SilentlyContinue
      }
      if (-not $exported) {
          Remove-Item -LiteralPath $partial -ErrorAction SilentlyContinue
          # Undo a replace that stopped half-way, so the previous export is back under its own name.
          if ((Test-Path -LiteralPath $replaced) -and -not (Test-Path -LiteralPath $final)) {
              Move-Item -LiteralPath $replaced -Destination $final
          }
      }
      Remove-Variable secure, url, uri, info, sep, user, pass, db, final, partial, replaced, swapping -ErrorAction SilentlyContinue
  }

  # 2. Report. The readability check (pg_restore --list) ran before the new file was put in place. It reads the
  #    archive's table of contents only; it is not a restore test. To prove the data restores, restore it into a
  #    scratch database ("Restore into a new, scratch database" in docs/backup-and-restore.md).
  if ($exported) {
      "Export saved: traceforge.dump"
      $list = pg_restore --list traceforge.dump
      $list | Select-String "dbname:|Dumped from"
      "tables: $(($list | Select-String ' TABLE public ').Count)   (21 at schema revision 0007)"
      "schema version recorded: $([bool]($list | Select-String 'TABLE DATA public alembic_version'))"
  } else {
      "No new export. traceforge.dump, if you had one, is your previous export and was not changed."
  }
  ```

  The dump contains password hashes and everything your agents recorded: keep it private and out of the repository.
  Free databases have no backups, so this file is your only copy.
- **Custom domain**: add it in Render, then set `TRACEFORGE_PUBLIC_URL`, `TRACEFORGE_ALLOWED_HOSTS` and
  `TRACEFORGE_CORS_ORIGINS` to it and update the OAuth callback URLs.

## Your own server (VPS)

This part puts Traceforge on one Linux server, behind [Caddy](https://caddyserver.com) for HTTPS. It keeps the
application's own design intact: one `python -m app.serve` process that listens only on `127.0.0.1`, PostgreSQL 16 in
Docker bound to `127.0.0.1`, and Caddy as the only thing reachable from the internet.

```
 Internet ──443/80──▶ Caddy (TLS, HTTP→HTTPS) ──127.0.0.1:8000──▶ python -m app.serve --database main
                                                                          │
                                                          127.0.0.1:5433 ─┴─▶ PostgreSQL 16 (Docker)
```

Read **[What this deployment does not change](#what-this-deployment-does-not-change)** before you start.

## 1. Requirements

- A Linux VPS (Ubuntu 24.04 LTS is assumed below; any systemd distribution works). 2 vCPU and 2 GB RAM are enough
  to start.
- A domain name whose `A` (and optionally `AAAA`) record points at the server. `traceforge.example.com` is used
  below; replace it everywhere.
- SSH access with `sudo`.

This VPS route keeps `app.serve` on loopback (`127.0.0.1`) with Caddy in front. Hosting platforms that run the app
in their own containers behind their own TLS proxy are a different route: Render is supported through
[`render.yaml`](render.yaml) and the opt-in `TRACEFORGE_PUBLIC_BIND` (see [Render (free plan)](#render-free-plan));
other platforms of that kind (Railway, Fly and similar) are untested.

## 2. Prepare the server

```bash
sudo apt update && sudo apt -y upgrade
sudo apt -y install git python3.11 python3.11-venv curl ufw debian-keyring debian-archive-keyring apt-transport-https

# Docker Engine and the compose plugin (https://docs.docker.com/engine/install/ubuntu/)
curl -fsSL https://get.docker.com | sudo sh

# Node.js 20+ to build the console once (https://nodejs.org); for example via NodeSource:
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash - && sudo apt -y install nodejs

# Caddy (https://caddyserver.com/docs/install#debian-ubuntu-raspbian)
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt -y install caddy

# A dedicated, unprivileged user that owns the application. It is in the docker group so it can run backups.
sudo useradd --system --create-home --home-dir /opt/traceforge --shell /usr/sbin/nologin traceforge
sudo usermod -aG docker traceforge
```

Membership of the `docker` group is equivalent to root on that machine; keep the account non-login as shown.

## 3. Get the code and build it

```bash
sudo -u traceforge -s /bin/bash   # work as the service user from here on
cd /opt/traceforge
git clone https://github.com/hemanth210205/Trace-forge.git .
git checkout <release tag or commit>   # deploy a known revision, not a moving branch

python3.11 -m venv .venv
.venv/bin/pip install -e "backend" -c backend/constraints.txt
.venv/bin/pip install -e sdk/python      # only needed if you run the sample agents on this server

cd frontend && npm ci && npm run build && cd ..   # produces frontend/dist, served by the application
exit
```

Note the revision you deployed (`git rev-parse HEAD`); rollback needs it.

## 4. Configure

All configuration is environment variables, read from `/opt/traceforge/.env`. Start from the production template,
which contains placeholders only:

```bash
sudo install -m 600 -o traceforge -g traceforge /opt/traceforge/deploy/.env.production.example /opt/traceforge/.env
sudo -u traceforge nano /opt/traceforge/.env
```

Generate every secret on the server, one at a time, and never reuse development values:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

| Variable | Production value | Why |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | new random value | Database password; also inside `DATABASE_URL` (URL-encode special characters) |
| `TRACEFORGE_SECRET_KEY`, `TRACEFORGE_API_KEY_PEPPER` | new random values, 32+ characters | Sign sessions; hash API keys. Changing the pepper invalidates every API key |
| `TRACEFORGE_PUBLIC_URL` | `https://traceforge.example.com` | Origin of the console; OAuth redirect URLs are built from it |
| `TRACEFORGE_ALLOWED_HOSTS` | `traceforge.example.com,127.0.0.1` | Any other `Host` gets 400; `127.0.0.1` keeps local health checks working |
| `TRACEFORGE_CORS_ORIGINS` | `https://traceforge.example.com` | Exact origin trusted for login and registration |
| `TRACEFORGE_COOKIE_SECURE` | `true` | Session cookies only over HTTPS |
| `TRACEFORGE_TRUSTED_PROXIES` | `127.0.0.1,::1` | Only Caddy, on loopback, may set `X-Forwarded-For` / `-Proto` |
| `TRACEFORGE_REGISTRATION` | `invite` or `disabled` to start | Who may create accounts, by password **and** by Google/GitHub |

**Trusted proxies.** Forwarded headers are read only when the request's direct peer is in
`TRACEFORGE_TRUSTED_PROXIES`; from anyone else they are ignored. Behind Caddy that gives the login rate limiter the
visitor's real address instead of one shared `127.0.0.1` budget. Because the list trusts loopback, any process on
this server could set those headers: run nothing else untrusted on it. Do not list addresses outside your own
infrastructure.

**Registration modes** (existing accounts can always sign in, whatever the mode):

| Mode | New accounts | Notes |
| --- | --- | --- |
| `open` | Anyone | The development default. Not recommended on the internet |
| `disabled` | None | Create accounts with `python -m app.accounts user create` (section 7) |
| `domain` | Emails in `TRACEFORGE_REGISTRATION_DOMAINS` | Password sign-up does not verify the address (Traceforge sends no email), so anyone may *claim* such an address with a password. Google/GitHub sign-in requires a provider-verified email. Prefer `invite` if that matters |
| `invite` | Holders of an invitation | An invitation is tied to one email, used once, expires (default 7 days) and can be revoked. Password sign-up needs its code; Google/GitHub sign-in needs a pending invitation for the verified email |

Leave `TEST_DATABASE_URL` and `DEV_DATABASE_URL` unset on the server: the production server runs only against the
main database, and the test suite (which truncates its database) must never run here.

## 5. Database

```bash
cd /opt/traceforge
sudo -u traceforge docker compose up -d postgres
sudo -u traceforge docker ps --filter name=traceforge-postgres   # wait for "healthy"
```

PostgreSQL listens on `127.0.0.1:5433` only and keeps its data in the Docker volume `traceforge_pgdata`. On first
start the image creates `traceforge` (production) and, from `docker/postgres/init/`, the empty `traceforge_dev` and
`traceforge_test` databases. Those two are never used on the server; leave them empty.

## 6. Migrations

`python -m app.serve --database main` never migrates: if the main database is not at the code's schema revision it
refuses to start. Migrating is a separate, explicit step, guarded by a confirmation argument. The current head is
**0007**; a new database goes through 0001 → 0007 in one command.

```bash
cd /opt/traceforge/backend
# On an existing database: back up first (section 13).
sudo -u traceforge ../.venv/bin/python -m alembic -x database=main -x confirm=traceforge upgrade head
sudo -u traceforge ../.venv/bin/python -m alembic -x database=main -x confirm=traceforge current   # expect 0007 (head)
```

Migrations 0006 (Google/GitHub identities) and 0007 (invitations) only add tables and make the password column
nullable; they change no existing rows. Their downgrades are covered in [Rollback](#16-rollback).

## 7. Create the first account

With `TRACEFORGE_REGISTRATION=disabled` or `invite` nobody can sign up yet. Shell access to the server is what
authorises creating accounts:

```bash
cd /opt/traceforge/backend
# Directly (asks for the password twice; nothing is echoed or logged):
sudo -u traceforge ../.venv/bin/python -m app.accounts --database main user create you@example.com --name "Your Name"

# Or with an invitation (prints a code and a link once; only a hash is stored):
sudo -u traceforge ../.venv/bin/python -m app.accounts --database main invite create you@example.com --days 3
```

The invitation link has the form `https://traceforge.example.com/register#invite=<code>`. The code is in the
fragment, which browsers never send to the server, so it does not appear in Caddy or application logs. Send it over
a private channel.

Managing invitations later:

```bash
python -m app.accounts --database main invite list            # pending; add --all for used, revoked, expired
python -m app.accounts --database main invite revoke <id or email>
python -m app.accounts --database main invite prune --older-than-days 30
```

(Run them as `sudo -u traceforge ../.venv/bin/python ...` from `/opt/traceforge/backend`, as above.)

## 8. Run as a service (systemd)

```bash
sudo cp /opt/traceforge/deploy/traceforge.service /etc/systemd/system/traceforge.service
sudo systemctl daemon-reload
sudo systemctl enable --now traceforge
systemctl status traceforge
journalctl -u traceforge -n 50 --no-pager   # "Traceforge on database 'traceforge' at revision 0007 ..."
```

The unit runs `python -m app.serve --database main --host 127.0.0.1 --port 8000` as the `traceforge` user with a
hardened sandbox. It restarts on crashes but **not** after exit status 2 (schema out of date or unsafe database
choice), because restarting cannot fix that: run section 6 and `sudo systemctl restart traceforge`.

## 9. HTTPS with Caddy

```bash
sudo cp /opt/traceforge/deploy/Caddyfile /etc/caddy/Caddyfile
sudo sed -i 's/traceforge.example.com/YOUR.DOMAIN/' /etc/caddy/Caddyfile
sudo mkdir -p /var/log/caddy && sudo chown caddy:caddy /var/log/caddy
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy gets and renews the certificate automatically (ports 80 and 443 must be reachable and DNS must point here),
redirects HTTP to HTTPS, and forwards to `127.0.0.1:8000`. It discards `X-Forwarded-*` headers sent by clients and
sets its own; Traceforge believes them only because the peer is loopback (`TRACEFORGE_TRUSTED_PROXIES`).

## 10. Firewall

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
```

Port 8000 (Traceforge) and 5433 (PostgreSQL) must not be reachable from outside. They are bound to `127.0.0.1`,
which also matters because Docker's published ports bypass `ufw` rules. Verify from another machine:

```bash

```

## 11. Google and GitHub sign-in

Optional; without credentials the buttons explain that sign-in is not set up. Production needs its own OAuth apps
(or extra redirect URIs), registered with the public HTTPS address:

- **GitHub** (an OAuth App holds one callback URL, so create a production app separate from your local one):
  Settings → Developer settings → OAuth Apps → New OAuth App. Homepage `https://YOUR.DOMAIN`, callback
  `https://YOUR.DOMAIN/api/v1/auth/oauth/github/callback`. Generate a client secret.
- **Google**: Cloud console → APIs & Services → Credentials → OAuth client ID (Web application). Authorised redirect
  URI `https://YOUR.DOMAIN/api/v1/auth/oauth/google/callback`. While the consent screen is in *Testing*, only the
  test users you list can sign in; publish it for everyone (the `openid email profile` scopes need no review).

Add `TRACEFORGE_GITHUB_CLIENT_ID/SECRET` and/or `TRACEFORGE_GOOGLE_CLIENT_ID/SECRET` to `/opt/traceforge/.env` and
`sudo systemctl restart traceforge`. `TRACEFORGE_PUBLIC_URL` must be exactly the origin you registered.

The registration mode applies to Google/GitHub too: in `invite` mode a first sign-in needs a pending invitation for
the provider-verified email; in `disabled` mode only existing accounts can sign in.

Provider sign-in puts a one-time authorization `code` (and the `state`) in the callback URL. Neither is logged:
Traceforge's own logs record paths without query strings, and the shipped `deploy/Caddyfile` filters its access log
so those values (and other token-like query parameters, the `state` in the redirect to the provider, the CSRF header
and URLs in `Referer`) are written as `REDACTED`. Caddy itself already redacts `Cookie`, `Set-Cookie` and
`Authorization`. This was tested with Caddy 2.10.2 by sending real callback requests through it and inspecting the log.

## 13. Backups

Use logical backups of the `traceforge` database (`pg_dump` custom format); they are consistent while the server
runs. Backups contain password and API-key hashes and everything your agents recorded: keep them private, off the
repository, and copy them off the server.

```bash
sudo install -d -m 700 -o traceforge -g traceforge /var/backups/traceforge
```

A cron entry is enough. As the `traceforge` user (`sudo crontab -u traceforge -e`):

```cron
# Daily at 03:15: dump inside the container, check the archive is readable, copy it out, keep 14 days.
15 3 * * * f=traceforge-$(date +\%Y\%m\%d-\%H\%M\%S).dump; docker exec traceforge-postgres sh -c "pg_dump -U \"\$POSTGRES_USER\" -d traceforge --format=custom --file=/tmp/$f && pg_restore --list /tmp/$f > /dev/null" && docker cp traceforge-postgres:/tmp/$f /var/backups/traceforge/$f; docker exec traceforge-postgres rm -f /tmp/$f; find /var/backups/traceforge -name 'traceforge-*.dump' -mtime +14 -delete
```

The dump is written inside the container and copied out with `docker cp` (never piped through the shell), and it
is copied only if `pg_restore --list` can read it. Check that files appear each day: `ls -lh /var/backups/traceforge`.

Then copy `/var/backups/traceforge` to storage outside the server (another machine, or object storage with
encryption), for example with `rsync` or `rclone` on a second cron entry. A backup that lives only on the server is
lost with the server.

Always take a fresh backup before migrating or upgrading.

## 14. Restore test

A backup counts only once it has been restored. Restore into a **scratch** database, check it, and drop it; the
production database is not touched:

```bash
f=/var/backups/traceforge/traceforge-YYYYMMDD-HHMMSS.dump
docker cp "$f" traceforge-postgres:/tmp/restore.dump
docker exec traceforge-postgres sh -c 'createdb -U "$POSTGRES_USER" traceforge_restore_check'
docker exec traceforge-postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d traceforge_restore_check --no-owner --exit-on-error /tmp/restore.dump'

# Same revision and plausible row counts as production:
docker exec traceforge-postgres sh -c 'psql -U "$POSTGRES_USER" -d traceforge_restore_check -Atc "select version_num from alembic_version"'
for t in users projects traces spans datasets evaluation_runs invitations; do
  docker exec traceforge-postgres sh -c "psql -U \"\$POSTGRES_USER\" -d traceforge_restore_check -Atc \"select '$t', count(*) from $t\""
done

docker exec traceforge-postgres sh -c 'dropdb -U "$POSTGRES_USER" traceforge_restore_check'
docker exec traceforge-postgres rm -f /tmp/restore.dump
```

Do this after setting up backups, and then regularly (monthly is a reasonable rhythm). Restoring over the real
`traceforge` database is a disaster-recovery step: stop Traceforge first (`sudo systemctl stop traceforge`), take a
backup of the current state, then follow `docs/backup-and-restore.md`.

## 15. Upgrading

```bash
cd /opt/traceforge
git rev-parse HEAD                        # note the current revision for rollback
# take a backup (section 13)
sudo -u traceforge git fetch && sudo -u traceforge git checkout <new tag or commit>
sudo -u traceforge .venv/bin/pip install -e "backend" -c backend/constraints.txt
cd frontend && sudo -u traceforge npm ci && sudo -u traceforge npm run build && cd ..
sudo systemctl stop traceforge
cd backend && sudo -u traceforge ../.venv/bin/python -m alembic -x database=main -x confirm=traceforge upgrade head && cd ..

curl -fsS http://127.0.0.1:8000/api/v1/health
```

## 16. Rollback

1. **Code only (no new migration in the release):** check out the previous revision, reinstall, rebuild the
   console and restart, as in section 15 without the migration.
2. **The release added a migration:** prefer restoring the backup taken just before the upgrade (section 14 shows how
   to verify it first). Alembic downgrades exist but are not all lossless:
   - `0007 → 0006` drops the `invitations` table (pending invitations are lost; accounts are kept).
   - `0006 → 0005` drops linked Google/GitHub identities **and deletes accounts that have no password** (created
     through Google/GitHub), because the 0005 schema cannot hold them. Do not run it on data you want to keep.

   ```bash
   sudo systemctl stop traceforge
   cd /opt/traceforge/backend
   sudo -u traceforge ../.venv/bin/python -m alembic -x database=main -x confirm=traceforge downgrade 0006   # example
   cd .. && sudo -u traceforge git checkout <previous revision>   # then reinstall, rebuild, start
   ```
3. Confirm with the health checks in section 12.

## 17. Operations

- **Logs:** `journalctl -u traceforge` (application) and `/var/log/caddy/traceforge-access.log` (requests: method,
  path, status, timing, client address and user agent; sensitive query values and headers appear as `REDACTED`).
  If you add query parameters that carry secrets, add them to the `request>uri query` filter in the Caddyfile.
  Application logs record each request's method, path (no query string), status and duration, never bodies or
  headers, and scrub keys, tokens and passwords from messages; invitation codes are never logged. Uvicorn's own
  access log is turned off (`app/serve.py`), because it would print full URLs.
- **Rotating secrets:** a new `TRACEFORGE_SECRET_KEY` signs everyone out; a new `TRACEFORGE_API_KEY_PEPPER`
  invalidates every API key (users must create new ones). Restart after editing `.env`.
- **System updates:** `sudo apt update && sudo apt upgrade`, and `docker compose pull postgres` within PostgreSQL 16
  (take a backup first).

## What this deployment does not change

- **One process.** The login rate limiter and the background recovery sweep live in the server process. Do not run
  several copies of the service against one database.
- **No email.** Traceforge sends no email: no password reset, no address verification for password sign-ups. Use
  `invite` or `disabled` registration, or Google/GitHub sign-in, accordingly.
- **The rest of `docs/release-checklist.md`** still applies: the Anthropic diagnosis provider is experimental, and
  interrupted work is marked failed rather than resumed.
